Отчет по лабораторной работе №3: Интерактивная система управления космической станцией
1. Общее описание
Данная работа является продолжением лабораторных работ №1 и №2. Основная цель — реализовать единую систему управления космической станцией, объединив модули и командный центр из предыдущих работ с помощью паттернов проектирования: Фасад, Посредник, Команда и Цепочка обязанностей.

Программа представляет собой консольное приложение с интерактивным вводом команд, позволяющее управлять модулями станции, распределять ресурсы и запускать исследования.

2. Выбранный контракт и сохранение совместимости
Согласно уточненному ТЗ, мы не переписывали старые работы с нуля, а адаптировали существующую модель.

Модули и атрибуты: Сохранены классы Module, Durability, EnergyConsumption, Capacity. Добавлены только необходимые поля (позиция, флаг активности).

Фабрики: Используются StandardModuleFactory и AdvancedModuleFactory из ЛР1. В них добавлен метод createModule(type, name) для создания модулей по строковому имени.

Станция и Центр: Класс CommandCenter выступает единым источником ресурсов и контейнером модулей. Прямого дублирования контейнеров нет.

Окружение: EnvironmentSystem является тонким адаптером над прежней моделью окружения из ЛР2.

3. Роли паттернов проектирования
Фасад (Facade)
Класс: StationFacade

Роль: Является единой точкой входа для пользователя. Он скрывает всю сложность системы: полученную строку он передает в цепочку обработчиков, а распознанные команды — выполняет и записывает в историю. Фасад не дублирует бизнес-логику, а делегирует её командам и медиатору.

Посредник (Mediator)
Класс: StationMediator

Роль: Координирует взаимодействие между модулями и системами (CommandCenter, EnergySystem, EnvironmentSystem). Модули не обращаются друг к другу напрямую. Например, при запросе энергии лабораторией, запрос идет через Медиатора, который решает, откуда взять энергию.

Команда (Command)
Класс: Command и его наследники (ActivateModuleCommand, BuildModuleCommand и др.)

Роль: Каждое действие пользователя инкапсулировано в объект команды. Это позволяет легко добавлять новые действия, логировать их и хранить историю (реализован CommandHistory).

Цепочка обязанностей (Chain of Responsibility)
Класс: Handler и его наследники (ActivateHandler, BuildHandler и др.)

Роль: Обрабатывает текстовый ввод. Каждый обработчик пытается распарсить свою команду. Если у него не получается — передает строку следующему. Если команда известна, но аргументы неверны (например, отрицательный процент энергии), обработчик выдает понятную ошибку, не выполняя частичных действий.

4. UML-схема архитектуры (Текстовое описание)
Архитектура программы представляет собой следующую иерархию и связи:

Точка входа (main): Создает все системы и запускает бесконечный цикл чтения команд, передавая каждую введенную строку в StationFacade::processInput().

Фасад (StationFacade): Хранит указатель на StationMediator и начало цепочки обработчиков (Handler). Также содержит CommandHistory.

Цепочка обязанностей (Handler): Абстрактный класс, имеющий поле next_ (указатель на следующего обработчика). Наследники (ActivateHandler, BuildHandler и др.) переопределяют метод handle(). Если обработчик распознал команду, он создает соответствующий объект Command и передает его в StationFacade::executeCommand().

Команды (Command): Абстрактный класс с виртуальным методом execute(). Каждая конкретная команда (например, RepairModuleCommand) хранит параметры (индекс модуля) и указатель на StationMediator. В методе execute() команда вызывает соответствующий метод медиатора.

Посредник (StationMediator): Центральный узел. Хранит указатели на CommandCenter, EnergySystem и EnvironmentSystem. Он принимает запросы от команд (например, requestEnergy()) и координирует работу подсистем.

Предметная область:

CommandCenter — хранит вектор модулей (std::unique_ptr<Module>) и ресурсы (энергия, кислород, безопасность).

EnergySystem — отвечает за выработку и распределение энергии.

EnvironmentSystem — хранит информацию о текущей среде.

Module (и наследники) — базовые элементы станции, имеют методы activate(), deactivate(), getStatus().

Взаимодействие: Пользователь -> Фасад -> Цепочка -> Команда -> Посредник -> Подсистемы.

Сценарий 4: Взаимодействие через посредника
Демонстрируется в логах выше. Лаборатория (модуль) запрашивает энергию, Посредник перехватывает запрос, обращается к EnergySystem, и только после этого энергия списывается. Модули не общаются с EnergySystem напрямую.

6. Инварианты интеграции
Программа проверена на соблюдение инвариантов:

Отсутствие отрицательных значений: При запросе энергии больше доступной, программа выдаст ошибку и не спишет ресурсы (проверено в CommandCenter::spendEnergy).

Нет частичных операций: Если ресурсов на ремонт или строительство не хватает, операция не выполняется, состояние станции не меняется.

Неверные индексы: При вводе несуществующего индекса модуля программа выдает понятную ошибку, не изменяя станцию.

Повторный просмотр: Команда status не тратит энергию и не наносит урон (просмотр пассивен).
